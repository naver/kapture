= kapture 2.0: changes
:toc:

== Command line

Since version 2.0, the `kapture_*` tools derive their command line from a type-hinted function
(link:https://jsonargparse.readthedocs.io[jsonargparse]), see `doc/tutorial.adoc` "Command line conventions".
Every tool now accepts `--config file.yaml` and `--print_config`.

== Conventions

* One canonical `snake_case` name per option, used as long flag, as `--config` key and as python parameter:
  `input` / `output` (`inputs` for a list), `force`, `image_transfer`, `verbose`, `quiet`, then tool specific
  names (`keypoints_type`, ...).
* All former long flags that differ from the canonical name are kept as *deprecated aliases*, and the dashed
  form of every flag is accepted (`--keypoints-type` and `--keypoints_type`). They may be removed in a later
  major version.
* Short flags are unchanged (`-i`, `-o`, `-v`, `-q`, `-f`/`-y`, `-k`, `-im`, `-db`, ...).
* `-v` alone still means `info`; `-v debug`, `-v 10` still work; `-q` / `--silent` / `--quiet` is now an
  independent flag instead of being mutually exclusive with `-v`.
* Booleans are flags with a negated form: `--force` / `--no_force`. Former `--no_xxx` flags still exist, as the
  negated form of a `xxx` option enabled by default (`--no_geometric_filtering`, `--no_cleaning`).
* Abbreviated long options (`--skip_rec` for `--skip_reconstruction`) are no longer accepted.
* Python 3.10 or newer is required.

== Behaviour changes

[cols="1,3"]
|===
| tool | change

| kapture_download_dataset
| the dataset names are no longer positional: `kapture_download_dataset install -d "RobotCar*"`
  (`--dataset`, `-d`, several names accepted). Global options (`--install_path`, `-v`) come before the
  subcommand, as before.

| kapture_rename_features
| `-f`/`-y`/`--force` removed: it was declared but had no effect.

| kapture_merge
| `--keep_sensor_ids` has a default (false) like on the command line; the python function
  `merge_kaptures` no longer requires it.

| kapture_import_utbm
| `--no-force_same_time` (mixed dash/underscore) is now `--no_force_same_time` / `--no-force-same-time`.

| kapture_export_depth_images
| `-r` must be given two values (`-r 0.1 10.0`); a wrong count is a clear error instead of a crash.

| kapture_export_openmvg, kapture_export_opensfm, kapture_import_rosbag, kapture_import_utbm,
  kapture_export_image_list
| `-f`, `-y` and `--force` are all accepted everywhere (`force` is unused by export_4seasons_pairs,
  export_ETH_MS_LTVL, export_LTVL2020, import_stereolabs, as before).
|===

== New camera models

`sensors.txt` accepts nine more camera models (see `kapture_format.adoc`): `OPENCV_OMNI` (unified / Mei model of the
OpenCV `omnidir` module: `w, h, fx, fy, cx, cy, s, xi, k1, k2, p1, p2`) and the models of COLMAP 3.12:
`RAD_TAN_THIN_PRISM_FISHEYE`, `SIMPLE_DIVISION`, `DIVISION`, `SIMPLE_FISHEYE`, `FISHEYE`, `EUCM`, `EQUIRECTANGULAR`,
`SKEWED_PINHOLE`. The format version stays 1.1, but a `sensors.txt` using one of them is rejected by kapture < 2.0.

* `kapture.CAMERA_TYPE_PARAMS_NAMES` gives the parameter names of every model; `Camera.camera_param('fx')` reads a
  parameter by name. Code indexing `camera_params[2]` as the focal must first check `camera_type`, since
  `EQUIRECTANGULAR` and `UNKNOWN_CAMERA` only have `w, h`. Known places in kapture-localization / kapture-internal:
  `tools/kapture_create_3D_model_from_depth.py`, `tools/register_floorplan.py`, `tools/kapture_export_debug_images.py`,
  `tools/kapture_import_caminfo.py`, `localization_lib/bundle_adjustment/bundle_adjustment.py`,
  `localization_lib/matching/geometric_verification.py`.
* `kapture.Camera` raises `ValueError` / `TypeError` with an explicit message (model, expected parameters) instead of
  `AssertionError` on an invalid model or parameter list.
* COLMAP import no longer crashes on camera models unknown to kapture: they become `UNKNOWN_CAMERA` with a warning.
  COLMAP export of the 3.12 models logs a warning (older COLMAP cannot read them); `OPENCV_OMNI` is exported as
  `EUCM` (unified model without distortion, warning logged), the original parameters stay in `sensors.txt`.
* OpenMVG: `EQUIRECTANGULAR` ↔ `spherical`, `FISHEYE`/`SIMPLE_FISHEYE` → `fisheye`, `SKEWED_PINHOLE` → `pinhole`;
  OpenSfM: `EQUIRECTANGULAR` ↔ `spherical`. Everything else unsupported raises `ValueError` naming the camera.
* `kapture.utils.open_cv.import_opencv_camera_calibration` (used by `kapture_import_utbm --camera_info`) returns an
  `OPENCV_OMNI` camera when the yaml has a `xi` entry.

== New `range` record type

`range` maps work like `depth` maps (camera-like sensor in `sensors.txt`, `records_range.txt`, float32
`records_data/*.range` files), but each value is the distance in meters to the sensor center instead of the distance
to its origin plane, so they are valid for any field of view (fisheye, equirectangular). Existing depth data keeps its
meaning. The format version stays 1.1. kapture < 2.0 reads a `range` sensor as a generic sensor and ignores
`records_range.txt`.

* `kapture.SensorType.range`, `kapture.RecordsRange`, `Kapture.records_range`.
* `kapture.io.csv.records_range_to_file` / `records_range_from_file`, loaded and saved by `kapture_from_dir` /
  `kapture_to_dir`.
* `kapture.io.records.get_range_map_fullpath`, `range_maps_to_filepaths`, `range_map_from_file`, `range_map_to_file`.
* `kapture_merge` merges range records and their files (`--skip records_range` to skip them).
* `kapture.SensorType.wifi` is now a regular enum value (it was `()`).

== New tool `kapture_extract_period`

Extracts some periods of time of a recording to a new kapture (sub-scenes of a long recording):

[source,bash]
----
$> kapture_extract_period -i full -o part --windows 1792656648559471 1792656685860184 --transfer link_relative
$> kapture_extract_period -i full -o part --relative --windows 120 157.5 300 340 -s lidar0_clean
----

* `--windows T0 T1 [T0 T1 ...]`: pairs of kapture timestamps, both included, or seconds since the first timestamp of
  the recording with `--relative` (`--time_unit`, default 1e6: microseconds); overlapping periods are merged.
* Keeps the sensors, rigs, trajectories and all the `records_*` of the periods, minus `--skip_sensors`. The
  reconstruction data (features, matches, points3d, observations) are not extracted.
* `--transfer` (default `skip`) brings the data files of the kept records and `sensors/raw`. Links point to the
  actual files, so an extraction of an extraction links to the original recording; a record whose data file is missing
  in the input is dropped with a warning.
* `<output>/subset.json` keeps the source, the periods and the number of records kept.
* Library: `kapture.algo.extract` (`normalize_windows`, `extract_period` in memory, `kapture_extract_period`).

== New tool `kapture_extract_area`

Extracts the part of a recording made in an area (a box aligned with the axes of the world frame, or a sphere) to a
new kapture: the periods are those the trajectory spends in the area, then everything works as `kapture_extract_period`
(same `--skip_sensors`, `--transfer`, `subset.json` with the area and the periods found).

[source,bash]
----
$> kapture_extract_area -i full -o part --box -15 45 25 80 -5 5 --transfer link_relative   # xmin xmax ymin ymax zmin zmax
$> kapture_extract_area -i full -o part --box -15 45 25 80 NONE NONE                       # no filter on z
$> kapture_extract_area -i full -o part --sphere -5.6 56.2 -2.5 6 -s lidar0_clean          # x y z radius
----

* The records are selected by the position of the device (rig or sensor of `trajectories.txt`), not by what they
  see: a scan or an image taken from inside the area is kept whole. Needs trajectories.
* `--gap` (default 5 s): two poses inside the area less than `gap` apart are in the same period, so a short way out
  does not cut it; `--pad` (default 0.2 s) is kept before and after every period; `--time_unit` as above.
* Both shapes are 3-D and make no assumption on the axes of the world frame (which one is vertical); their borders
  are included.
* `NONE` instead of a value of `--box` means no bound on that side (`--box NONE 45 NONE NONE NONE NONE`: x <= 45).
* `--crop_points3d` also extracts the points3d inside the area (off by default: the whole `points3d.txt` is loaded);
  the other reconstruction data are not extracted.
* Library: `kapture.algo.extract` (`trajectory_positions`, `box_bounds`, `points_in_box`, `points_in_sphere`, `box_area`,
  `sphere_area`, `windows_in_area`, `kapture_extract_area`).

== Python API changes

Tool functions in `kapture.tools.*` take the canonical parameter names and two new keyword parameters
`verbose` and `quiet`. Library converters in `kapture.converter.*` are unchanged. Notable signature changes:

* `import_image_list(inputs, output, images='', ...)` and `import_image_list_with_poses(input, output, images,
  calibration, ...)`: positional order changed, call them with keywords.
* `import_7scenes` / `import_12scenes`: default `image_transfer` is now `link_absolute` (the command line default),
  it was `skip` when called from python.
* `import_bundler` / `import_nvm`: `ignore_trajectories` and `add_reconstruction` default to `False`.
* `merge_kaptures`: `keep_sensor_ids` defaults to `False`.

Known downstream use: `kapture_localization` imports `import_idl_dataset_cvpr17` from
`kapture.tools.kapture_import_IDL_dataset_cvpr17`; its signature is now
`import_idl_dataset_cvpr17(input, output, gt_path=None, force=False, image_transfer=TransferAction.link_absolute,
verbose='warning', quiet=False)`.
